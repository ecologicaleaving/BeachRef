### VIS API Integration Specifications

**Request Format Requirements** [Source: referee-extraction-implementation-guidelines.md#API Request Pattern]:
```xml
<Request Type="GetEventOfficialList" Fields="FederationCode FirstName Gender LastName NoOfficial Role Status Type">
  <Filter NoEvent="1601"/>
</Request>

<Request Type="GetEventRefereeList" Fields="FederationCode FirstName Gender LastName NoReferee Status Type TheoryTest StrongPoints WeakPoints">
  <Filter NoEvent="1601"/>
</Request>
```

**Critical Field Distinctions** [Source: referee-extraction-implementation-guidelines.md#Core Requirements]:
- `NoOfficial` - Official identification number for officials list
- `NoReferee` - Actual referee identification number (NOT registration number)
- Field specification mandatory for all `GetXxxList` requests per VIS API requirements

### Existing Patterns to Follow

**XML Request Building Pattern** [Source: api-specifications.md#Implementation Example]:
- Use existing form data encoding (not SOAP)
- Follow established XML request builders from current methods
- Implement field selection optimization using existing `getOptimizedFields()` patterns

**Response Parsing Pattern** [Source: api-specifications.md#Enhanced Behavior Flow]:
- Use existing `VisResponseParser` extension patterns
- Handle XML response transformation following current match/tournament parsing
- Maintain data validation and error handling consistency

**Type Definition Pattern** [Source: architecture analysis]:
- Follow readonly interface patterns from existing VIS types
- Use proper numeric types for VIS fields (not strings) per VIS compliance requirements
- Implement discriminated unions for different referee roles/statuses

### Error Handling Integration
- Extend existing `ConnectionCircuitBreaker.ts` patterns for referee-specific operations [Source: referee-extraction-implementation-guidelines.md#Circuit Breaker Pattern]
- Use established timeout and retry logic from existing API methods
- Implement proper fallback hierarchy following current service patterns

### Performance Considerations
- Field selection optimization acceptable due to daily caching strategy (vs frequent polling)
- Extended field lists (`TheoryTest`, `StrongPoints`, `WeakPoints`) justified by 24-hour TTL
- Memory footprint minimal due to referee data size vs tournament/match data volume
