## Story
**As a** BeachRef developer,  
**I want** to consolidate fragmented match interfaces into a unified VIS-compliant architecture,  
**so that** the application uses a single source of truth for match data with consistent type safety and eliminates conversion overhead between interface types

3. **Update match display components** (`MatchList`, `MatchCard`) to work with new data structure while maintaining identical visual behavior
4. **Remove legacy interfaces and update all import statements** after successful migration to prevent future fragmentation

### Interface Consolidation Requirements
**Source: [docs/architecture/vis-api-data-structure-improvement-plan.md#data-model-fragmentation]**

**Current Fragmented Interface Problem:**
- `BeachMatch` (types/match.ts) - Legacy string-based interface currently used in match display components
- `BeachLiveMatch` (types/beach-live.ts) - Real-time match updates with additional live-specific fields
- `BeachMatchCore` (types/match-v2.ts) - Core domain model with computed fields and match status handling
- API types (types/api-v2.ts) - Raw API response interfaces for VIS integration

**Issues with Current Architecture:**
- Type confusion across services requiring constant interface conversion
- Duplicate field definitions creating maintenance overhead  
- Conversion overhead between types impacting performance in match list rendering
- Inconsistent data validation across different interface implementations

**Target Unified Architecture:**
**Source: [docs/architecture/vis-api-data-structure-improvement-plan.md#phase-3-unified-architecture]**
- Single `VisCompliantMatch` interface as source of truth for all match data
- Layered approach: `VisMatchRaw` → `MatchDomain` → `MatchPresentation` for different use cases
- Domain layer with computed fields (duration, status, importance, display formatting)
- Presentation layer optimized for UI components with pre-computed display strings
